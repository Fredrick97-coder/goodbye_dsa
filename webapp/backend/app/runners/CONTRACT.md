# Driver contract

A **driver** grades one submission in one language. Adding a language means
writing one of these, adding a row to `app/languages.py`, and (for the container
sandbox) a Dockerfile. Nothing else in the codebase changes.

`child_runner.py` (Python) and `ts_runner.mjs` (Node) are the two reference
implementations. The Node one is ~330 lines including comments.

## Invocation

The executor runs the argv from the language row's `command`, with these holes
substituted:

| hole | meaning |
|---|---|
| `{driver}` | absolute path to this file |
| `{workdir}` | directory containing the staged source |
| `{python_root}` | the curriculum root (Python driver only) |
| `{python}` | the server's interpreter (Python driver only) |

The job arrives as **one JSON object on stdin**. The report must be **one JSON
object on stdout, and nothing else** — the parent parses stdout, so anything the
submission prints has to be captured, not passed through.

## Job

```json
{
  "source":     "the submitted text",
  "sourceFile": "/work/solution.mts",
  "topic": 3, "num": 1,
  "mode": "test" | "run",
  "language": "typescript",
  "plan": { "targets": [ ... ] },
  "cpuSeconds": 5,
  "memoryMb": 512
}
```

The **parent writes `sourceFile`**; a driver must never write to disk. That is
what lets a driver run under a sandbox profile that forbids all writes.

`plan` is the language-neutral test plan generated by
`python/_harness/fixtures.py`. Each target is:

```json
{ "name": "reverse_string", "compare": "exact", "tol": null,
  "inplace": false, "note": "",
  "cases": [ { "args": ["hello"], "expected": "olleh" } ] }
```

`compare` is one of `exact`, `sorted`, `sorted_pairs`, `sorted_inner`. These
mirror the normalisers in `_harness/spec.py` and **must mean the same thing in
every driver** — two drivers disagreeing about whether an answer is correct is a
grading bug that only shows up in one language. `tol`, when set, is an absolute
tolerance for float comparison.

## Report

```json
{
  "ok": true,
  "compileError": null,
  "stdout": "whatever the submission printed",
  "targets": [
    { "target": "reverse_string", "status": "PASS", "note": "",
      "passed": 42, "total": 42,
      "cases": [ { "name": "case 1", "passed": false, "input": "...",
                   "expected": "...", "got": "...", "error": "" } ] }
  ]
}
```

`status` is `PASS`, `FAIL`, `STUB`, `ERROR`, `MISSING` or `RAN`.

Getting **`STUB` right matters most.** It is the difference between telling a
learner "not attempted" and telling them their untouched starter is wrong. The
rule: if the source shows an unwritten body, the status is `STUB` even though the
placeholder return is a real value. Python detects this with an AST check;
TypeScript cannot rely on the return value at all, because a starter has to
return `""`/`0`/`[]` for the file to compile.

`cases` is for the learner, so cap it (both reference drivers show at most three
failures) — a 40-case dump is not a diagnosis.

## Requirements a driver must satisfy

1. **Only JSON on stdout.** Capture the submission's output into `stdout`.
2. **Enforce `cpuSeconds` itself.** Python gets `RLIMIT_CPU` from the OS; Node
   has no equivalent, so `ts_runner.mjs` grades in a worker thread and terminates
   it from the main thread. A same-thread watchdog does not work: a tight loop
   blocks the event loop and the timer never fires.
3. **Deep-copy arguments per case**, so a solution that mutates its input cannot
   corrupt the next case — and so `inplace` can be compared against a pristine
   copy.
4. **Accept both the stated name and the language's idiomatic form.**
   `reverse_string` and `reverseString` both work in the Node driver.
5. **Never crash without emitting a report.** Wrap everything; a driver that dies
   silently is indistinguishable from a broken platform.
